01

The Customer Problem: Dark Tuesday.

LEVEL 100
THE INCIDENT
Start Here

Lab 7 gave our agents memory. Lab 8 gave them a governed front door. Both are running in production. And last Tuesday, the fraud-scoring agent approved a $91,500 cross-border transfer that should have been blocked.

Nobody noticed for fourteen hours. When they did, it took the full engineering team another six hours just to find the root cause. The agent was a black box.

Today we fix that. By the end of this lab, you will reproduce the same bug and find the root cause in two minutes.

NovaPay's fraud-scoring agent processed transaction TXN-DT-091 — a $91,500 cross-border transfer from NGN (Nigerian Naira) to GHS (Ghanaian Cedi). The sender had three high-risk flags. The agent approved it.

The agent called two tools in sequence: check_sender_history to pull the sender profile, and score_transaction_risk to compute a risk score.

The history check returned sender_flags=3 — high risk. But the scoring function has a default parameter: sender_flags: int = 0. The model called both tools independently rather than chaining the output of the first into the input of the second.

With sender_flags=0 (the default), the risk score was 45 — approve. With the actual sender_flags=3, the score would have been 99 — block.

"Look at the incident table. The agent called both tools and both tools returned correct data. So where is the bug?" Students will initially guess the scoring function is broken, or that sender_flags was corrupted. The real answer: the bug is in the gap between the two tools. The model called them independently — it got the flags from one tool and the score from another, but never connected them. No single tool has a bug. The orchestration is the bug. And without tracing, that gap is invisible.
Without observability, the compliance team's question — "why was this approved?" — requires reading CloudWatch logs from three services, correlating by timestamp, and manually reconstructing the call sequence. With OTEL tracing, the answer is a single trace ID query: open the trace, see that sender_flags_input=0 and used_default_flags=True, and the root cause is on screen in under two minutes.
02

Why Observability Is Different for AI Agents.

LEVEL 100
THE CONCEPT
Why This Is Hard

You already know how to instrument a web service. Request comes in, handler runs, response goes out. You log the status code and the latency. If something breaks, you search by request ID. That model does not work for agents.

An agent's execution path is non-deterministic. The same input can produce different tool sequences, different parameter choices, different numbers of steps. The model is making reasoning decisions at every step, and each decision is invisible unless you instrument it.

Traditional App Observability
  • Request → handler → response (deterministic path)
  • HTTP status codes tell you pass/fail
  • One call per request — latency is a single number
  • Parameters come from the caller (known, validated)
  • Bugs are in the code — reproduce with the same input
  • Logging the response body is usually sufficient
AI Agent Observability
  • Multi-step reasoning — path chosen at runtime by the model
  • Every tool call returns 200 OK even when the data is wrong
  • Multiple tool calls per request — latency is a tree
  • Parameters chosen by the model (may use defaults silently)
  • Bugs are in the orchestration gap — same input, different trace
  • You must log what the model chose, not just what the tool returned
THE KEY INSIGHT FOR THE ROOM In Dark Tuesday, both tool calls returned HTTP 200. Both tools executed correctly. The bug is that the model used a default parameter instead of chaining one tool's output into another's input. No amount of HTTP-level monitoring catches this. You need to see what arguments the model chose and whether those arguments came from a previous tool's output or from a default value.
ConceptDefinitionNovaPay Example
TraceThe full lifecycle of a single request through the system, from agent invocation to final responseThe entire fraud-scoring session for TXN-DT-091 — both tool calls, the model's reasoning, the final approval
SpanA single unit of work within a trace — a function call, a tool invocation, a model inferencecheck_sender_history is one span; score_transaction_risk is another; each has a parent span (the agent loop)
AttributeA key-value pair attached to a span that records a specific fact about the operationnovapay.sender_flags_input=0, novapay.used_default_flags=True
EventA timestamped annotation on a span, recording something noteworthy that happened during executionrisk_warning: high_amount_with_default_flags — fires when the amount is large but flags are suspiciously zero
Think of an airline's flight data recorder — the black box.

You do not need the flight recorder for the 99.97% of flights that land safely. But when one does not, the recorder is the only thing that tells you what happened. You cannot go back and add one after the crash.

OTEL instrumentation is the same. The overhead is negligible (~2ms per span). The cost of not having it is fourteen hours of log-diving when something goes wrong — and in a regulated business, a compliance incident report that says "we don't know why this was approved."

Students will ask: "Why not just add more logging?" This is the most important distinction to land. Logs are unstructured text. You can grep them, but you cannot query them by parameter value, correlate them across services, or build alarms on structured fields. Spans with attributes are structured data. You can query "show me every trace where used_default_flags=True AND amount > 50000" — and that query is the one that finds Dark Tuesday in two minutes.

Level 200 Deep Dive: Instrumented Tools.

LEVEL 200
THE CODE
Uninstrumented

Before we instrument, let us see what not instrumenting looks like. Here is score_transaction_risk without any tracing. It works. It returns the right answer. And when the model calls it with default flags, you will never know.

Uninstrumented score_transaction_riskPython — what students see first
def score_transaction_risk(
    transaction_id: str,
    amount: float,
    sender_flags: int = 0,       # <-- the dangerous default
    corridor: str = "domestic",
) -> dict:
    base = 20
    if amount > 50_000: base += 25
    if corridor != "domestic": base += 15
    base += sender_flags * 18     # flags=3 adds 54 points
    score = min(base, 99)
    return {
        "transaction_id": transaction_id,
        "risk_score": score,
        "recommendation": "block" if score >= 70 else "approve",
    }

Line 4 — sender_flags: int = 0. This is the trap. If the model does not explicitly pass sender_flags from check_sender_history, the scorer silently uses zero, and a high-risk sender gets a clean score. The function is correct — it does exactly what its signature says. The bug is upstream, in the model's parameter choice.

Line 8 — base += sender_flags * 18. With flags=3, this adds 54 points, pushing the total to 99 (block). With flags=0, it adds nothing, leaving the total at 45 (approve).

Run the uninstrumented version. Call check_sender_history("SENDER-001") and then score_transaction_risk("TXN-DT-091", 91500.0, corridor="NGN_GHS") without passing sender_flags. Observe: the score is 45, recommendation is "approve". Now ask: "Where would you look to debug this?" — There is nothing to look at. No trace, no span, no attribute. Just the return value.
Instrumented

Now the same function, with OTEL instrumentation. The logic is identical — we have added zero business logic changes. What we have added is visibility: custom attributes that record exactly what the model chose, and an event that fires when something looks suspicious.

Instrumented score_transaction_riskPython — the key diff
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import InMemorySpanExporter

exporter = InMemorySpanExporter()
provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(exporter))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("novapay.fraud")

def score_transaction_risk(
    transaction_id: str,
    amount: float,
    sender_flags: int = 0,
    corridor: str = "domestic",
) -> dict:
    with tracer.start_as_current_span("score_transaction_risk") as span:
        # Record what the model chose
        span.set_attribute("novapay.transaction_id", transaction_id)
        span.set_attribute("novapay.amount", amount)
        span.set_attribute("novapay.sender_flags_input", sender_flags)
        span.set_attribute("novapay.corridor", corridor)
        # THIS is the root-cause indicator
        span.set_attribute("novapay.used_default_flags", sender_flags == 0)

        base = 20
        if amount > 50_000: base += 25
        if corridor != "domestic": base += 15
        base += sender_flags * 18
        score = min(base, 99)

        # Suspicious pattern: high amount + default flags
        if amount > 50_000 and sender_flags == 0:
            span.add_event("risk_warning", {
                "warning": "high_amount_with_default_flags",
                "amount": str(amount),
                "sender_flags": str(sender_flags),
            })

        span.set_attribute("novapay.risk_score", score)
        span.set_attribute("novapay.recommendation",
            "block" if score >= 70 else "approve")
        return {"transaction_id": transaction_id,
                "risk_score": score,
                "recommendation": "block" if score >= 70 else "approve"}

Line 24 — span.set_attribute("novapay.used_default_flags", sender_flags == 0). This single attribute IS the root cause indicator. When you query your traces for used_default_flags=True AND amount > 50000, every Dark Tuesday incident appears instantly. No log parsing. No guessing.

Lines 32-36 — span.add_event("risk_warning", {...}). The event fires a domain-specific warning when a suspicious pattern occurs: high-value transaction with default flags. Events are timestamped annotations — they tell you not just that something happened, but that the system noticed it was suspicious. This becomes the basis for a CloudWatch alarm in Level 400.

Lines 1-8 — InMemorySpanExporter. In development, spans are collected in memory and can be inspected programmatically. No Collector, no X-Ray account, no infrastructure. In production, you swap this for an ADOT Collector that exports to X-Ray. The instrumentation code does not change.

Instrumentation adds approximately 2ms per tool call of overhead. For a fraud-scoring pipeline where the model call alone takes 800-2000ms and the tool execution takes 50-200ms, 2ms is invisible. The trade-off is maintenance: every time the tool signature changes, the span attributes must change with it. Treat your instrumentation as part of the tool's contract, not as an afterthought.
"Why not just add print(f"sender_flags={sender_flags}")?" — This is the most important question students will ask. The answer: a print statement produces an unstructured string in a log stream. You can grep for it, but you cannot query it as a typed field, you cannot build an alarm on it, you cannot correlate it with spans from other services, and you cannot see it in a trace waterfall. Structured attributes are queryable, alertable, and correlated. That is the difference between logging and observability.

Level 300 · b

CloudWatch Log Delivery — the new piece

CloudWatch log delivery is a three-step process: tell CloudWatch where the logs come from (the source), where they should go (the destination), and then connect the two (the delivery). You do this twice — once for application logs, once for traces.

Log Delivery Setup — APPLICATION_LOGSPython — the critical new code
# Step 1: Delivery Source — "where do the logs come from?"
logs.put_delivery_source(
    name=f"novapay-gw-app-src-{RUN_ID}",
    resourceArn=GATEWAY_ARN,
    logType="APPLICATION_LOGS",
)

# Step 2: Delivery Destination — "where do the logs go?"
logs.put_delivery_destination(
    name=f"novapay-gw-app-dst-{RUN_ID}",
    outputFormat="json",
    deliveryDestinationConfiguration={
        "destinationResourceArn": LOG_GROUP_ARN,
    },
)

# Step 3: Create the Delivery — "connect source to destination"
logs.create_delivery(
    deliverySourceName=f"novapay-gw-app-src-{RUN_ID}",
    deliveryDestinationArn=DEST_ARN,
)

put_delivery_source — tells CloudWatch that this gateway ARN produces APPLICATION_LOGS. The logType parameter is critical: it must be either APPLICATION_LOGS (structured log events) or TRACES (X-Ray trace segments). Each type requires its own delivery.

put_delivery_destination — tells CloudWatch where to send the logs. For APPLICATION_LOGS, the destination is a CloudWatch Log Group ARN. For TRACES, it would be an X-Ray group. The outputFormat of json ensures structured output you can query with CloudWatch Insights.

create_delivery — connects the source to the destination. Until this call completes, the gateway produces telemetry but it is not routed anywhere. This is the moment the gateway becomes observable.

YOU NEED TWO DELIVERIES One delivery for APPLICATION_LOGS (gateway request logs, auth events, errors) going to a CloudWatch Log Group. A second delivery for TRACES (distributed trace segments) going to X-Ray. They are independent — you can have one without the other. In this lab we set up both because the trace segments are what let you see the full span waterfall, and the application logs are what CloudWatch Alarms query against.

Log delivery has a propagation delay of 1-3 minutes.

  • After create_delivery returns, there is a window where the delivery exists but logs have not started flowing. If students query CloudWatch immediately and see nothing, they will think the setup failed.
  • The lab includes a wait-and-retry pattern. Warn students before they reach this step: "The delivery is created. It takes one to three minutes before logs appear. We will make a test call and then query."
  • This is the same class of eventual consistency as the Cognito domain resolution in Lab 8 — AWS control plane operations are not instantaneous.

Level 400: Production Operations.

LEVEL 400
OPERATING IT
CloudWatch Alarms

Tracing tells you what happened after someone asks. Alarms tell you something happened before anyone asks. In a regulated business, the difference between "we found it" and "compliance found it" is the difference between an internal fix and a regulatory incident.

ALARM 01

Error Rate Spike

Metric filter on the APPLICATION_LOGS group for status=ERROR. Threshold: more than 5 errors in any 5-minute window. Catches tool failures, auth rejections, and gateway errors before they cascade.

FIRES WHEN: tools start failing or auth is misconfigured
ALARM 02

Default-Flag Usage

Custom metric on used_default_flags=True events in the trace data. Threshold: any occurrence on a transaction above $50K. This alarm would have caught Dark Tuesday within minutes of it happening.

FIRES WHEN: the model uses default parameters on high-value transactions
ALARM 03

Latency SLA

P99 latency on gateway tool calls exceeding 5 seconds. Catches Lambda cold starts, backend degradation, or retry storms before they affect the user experience.

FIRES WHEN: something in the pipeline is slow
Sampling Strategy

You cannot trace everything. At NovaPay's volume, tracing every transaction would cost more than the transactions themselves. But you must trace failures and high-value operations. The sampling strategy is the trade-off between cost and debuggability.

CategorySample RateRationale
Baseline10%Enough to build latency distributions and detect trends. Low enough to keep costs manageable.
High-value (>$50K)100%Regulatory requirement: every high-value transaction must be auditable. Dark Tuesday was a $91,500 transaction.
Errors100%Every error is traced. You cannot debug what you did not capture. Errors are rare enough that 100% sampling is cheap.
Cross-border100%Compliance reporting requirement for cross-border corridors. The NGN-GHS corridor in Dark Tuesday would always be traced.
The baseline rate of 10% means you will miss 90% of routine transactions. If a low-value, domestic transaction triggers a subtle bug, you may not have the trace. The alternative — 100% baseline — costs roughly 10x more (~$39/month vs ~$3.90/month at NovaPay's volume). For most businesses, the 10% baseline with 100% on errors and high-value is the right starting point. Adjust after you see real traffic patterns, not before.
X-RAY SAMPLING RULES X-Ray supports rule-based sampling: you can set different rates for different URL patterns, HTTP methods, or custom attributes. The lab demonstrates this with a rule that samples 100% of requests where the path matches /high-value/* and 10% for everything else. The rules are evaluated server-side, so the client does not need to make sampling decisions.

Session Correlation

OTEL Baggage — stitching traces across boundaries

When a customer session spans multiple agents or multiple gateway calls, you need a common identifier that travels with the request. OTEL Baggage is the standard mechanism — a key-value pair that propagates across process boundaries.

from opentelemetry import baggage
from opentelemetry.context import attach, detach

# Set a session ID that follows the trace across all services
ctx = baggage.set_baggage("novapay.session_id", session_id)
token = attach(ctx)

try:
    # All spans created in this context carry the session_id
    with tracer.start_as_current_span("fraud_check_session") as span:
        span.set_attribute("novapay.session_id", session_id)
        # ... tool calls happen here ...
finally:
    detach(token)
In Dark Tuesday, the fraud-scoring agent was one of three agents involved in the customer's session. The support agent had already pulled the customer's profile. The collections agent had flagged a related account. Without session correlation, these three traces are isolated islands. With baggage carrying novapay.session_id, you can query "show me everything that happened in this customer's session" and see all three agents' traces in one view.

The observability tax — the ongoing cost nobody budgets for.

  • Every time a tool's signature changes, the span attributes must change with it. If you add a parameter, you need a new attribute. If you rename one, the old attribute becomes stale and queries break.
  • This is a maintenance burden that scales linearly with the number of instrumented tools. At NovaPay's current 6 tools, it is trivial. At 31 tools across six teams, it requires a shared library and a testing strategy.
  • Budget for it. Include instrumentation updates in every tool-change PR. Treat span attributes as a published API: changing one is a breaking change for anyone querying it.
There is a tension between observability depth and noise. Instrument everything and you have 200 attributes per span, most of which nobody ever queries. Instrument too little and the one attribute you need is the one you did not add. The heuristic: instrument the decision points — the places where the model makes a choice (which tool, which parameters, whether to chain) and the places where a default value could mask a bug. If you find yourself adding an attribute "just in case," stop. Add it when a real incident proves you need it.
The observability tax is like maintaining a fire suppression system.

You test it quarterly. You replace the sensors when you renovate a floor. You never question the cost — because the one time you need it and it is not there, the building burns down. But you also do not install sprinklers in the parking garage. You instrument the decision points, not every square foot.

UNDERSTANDING
Concept Questions
// five concept questions — ask before declaring the module complete
  • What is the difference between a trace and a span? Use the Dark Tuesday example.
  • Why are structured span attributes better than log lines for diagnosing agent bugs?
  • Explain the sampling trade-off: why not trace 100% of everything?
  • What are the three steps to set up CloudWatch log delivery for a gateway?
  • Why does the used_default_flags attribute matter more than the risk_score attribute?

Answers

1 · Trace vs Span

A trace is the full lifecycle of the fraud-scoring session for TXN-DT-091 — from agent invocation through both tool calls to the final approval. A span is one unit of work within that trace: check_sender_history is a span, score_transaction_risk is another span, and the agent loop itself is their parent span. Spans nest to form a tree; the trace is the tree.

2 · Attributes vs Log Lines

Log lines are unstructured text: INFO: sender_flags=0. You can grep for it, but you cannot query "show me all traces where sender_flags=0 AND amount>50000" without parsing. Span attributes are typed key-value pairs: novapay.sender_flags_input=0 (integer). You can query, filter, aggregate, and alarm on them directly. CloudWatch Insights, X-Ray, and every OTEL-compatible backend understands them natively.

3 · Sampling Trade-Off

At NovaPay's volume, 100% tracing costs ~$39/month. At 10% baseline with 100% for errors and high-value, it costs ~$3.96/month. The risk: a low-value domestic transaction triggers a subtle bug, and you have a 90% chance of not having the trace. The mitigation: 100% sampling on errors (the bug will be traced on its next occurrence) and on high-value transactions (where the business risk justifies the cost).

4 · Three Steps for Log Delivery

(a) put_delivery_source — tells CloudWatch that this gateway ARN produces logs of a specific type (APPLICATION_LOGS or TRACES). (b) put_delivery_destination — tells CloudWatch where to send them (a Log Group ARN or X-Ray). (c) create_delivery — connects the source to the destination. Two deliveries total: one for app logs, one for traces.

5 · Why used_default_flags Matters More

The risk score (45) tells you the outcome. The used_default_flags=True attribute tells you the cause. The score is correct given its inputs — the bug is that the inputs were wrong. Without the default-flag indicator, you would investigate the scoring algorithm, the threshold, the business rules — everything except the actual problem, which is that the model did not chain the tools. The root-cause attribute points you to the gap, not the symptom.
